# v4 空括号条头前缀识别

用户已授权持续完善和真实语料发布。本设计在既有来源保留、v4 独立版本及有界结构恢复规则内实施，不改变产品或证据审批边界。

## 证据与选择

实际 `_row_args → _prepare → _require_importable` 对残余32源的审计为 `artifacts/legal-corpus/full-release/residual32-v4-parser-audit-20260906T204447Z.json`，32份仍未通过完整条序列。原始 ZIP Loader 的早期审计不代表实际导入：乌鲁木齐来源在 Word XML 中存在 `第三十<w:tab/>五条`，ExportReader正确保留制表符后仍漏识别，不能计为修复完成。

本次只处理双鸭山山体绿线条例，source SHA 前缀 `e358667a7f`，既有转换载体段落21为 `（） 第十条 ...`，正文中的条号明确存在，第九条及第十一条可闭合。原件是 `.doc`，使用已验证转换目录；不重做转换、不修改原件。前文末尾多出的“发”与该条头识别是不同问题，保留原样，本次结构通过不是全文法律质量验收。

选择扩展已有 `prefixed_article` 的精确前缀候选，比新增第二个近似检测器更小、更容易保持相同锚点及引号边界。无差别删除标点会误识别引用，不采用。按来源哈希或标题豁免质量检查会掩盖结构问题，不采用。

## 约束

- 仅精确 `corpus-docx-v4` 生效；默认、v3、相似版本名行为不变。
- 新候选只接受段首恰好全角空括号 `（）` 加至少一个水平空白，随后普通条头、水平空白和非空正文。原有 U+E004 加水平空白行为保持不变。
- ASCII括号、括号内有文字/数字/空白、重复前缀、混合前缀、换行分隔均不加入白名单。无条号后正文分隔、补充条和条款引用不恢复。
- 继续使用已有左右普通条号锚、连续精确序列、章节及补充条屏障、引用/括号闭合规则；没有锚点、重复、逆序、缺号或边界不确定仍不恢复。括号前缀是原文中的空括号，不是引用边界豁免。
- 原 ParsedDocument、条文 text/paragraphs、前缀、空白及段落 ordinal 不变。新增识别沿用 PrefixedArticleSpan，marker_start 与原 prefix 精确对应。只调整分类视图，不能改写存储正文。
- 不修改 Loader、质量门禁、导入 Schema、旧版本事实及完整报告。v4尚未全局冻结，本次不启动v4导入长任务。
- 不改运行中的5项 embedding runtime，不加载模型、不启动OpenSearch、不改变显卡设置。保持既有CPU接续。

## 验收

合成测试先证明当前版本漏识别；再验证合法单源/候选组、前缀保留、版本隔离及上述拒绝边界。实际目标经 CLI 预检、全条序列、层次分块及叶子覆盖核对；原件与转换件SHA在前后不变，旧/v4全文字符拼接相同。重跑既有7源前缀样本及残余32源审计，记录局部结果，不把它宣称为全部语料或生产发布完成。后端测试、Ruff、mypy及独立代码复审通过后更新现状。
